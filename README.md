## 怎么跑起来

这个项目是 **Node.js + TypeScript**，不是 Java —— 不需要 JDK、Maven、Gradle，也没有编译步骤。
唯一前置条件是 Node.js ≥ 22（内置类型擦除，`.ts` 直接执行），仓库零运行时依赖，**不需要 `npm install`**。

```bash
node --version                      # 需要 v22 或更高
cd track-pi && npm start            # 启动，默认 http://127.0.0.1:18150/
```

浏览器打开 <http://127.0.0.1:18150/> 就是完整界面（前端构建产物由同一个服务托管）。
试试：`查一下余额` / `转给小王 100 元` / `取消云幕视频会员` / `把理财全部赎回`。

**打开就能用，不用起服务**。两个页面都是单文件、零外部依赖，双击即可：

| 页面 | 双击打开 | 说明 |
|---|---|---|
| `web/dist/index.html` | 业务界面 | 说一句话办一笔业务，账户、审计、确认都在右边 |
| `web/public/demo.html` | 演示站 | 六个面板讲清每条判定怎么来的：对话、补槽、令牌、幂等回放、工单、运维 |

两个页面内嵌的都是**同一份引擎** —— 用 esbuild / vite 把真正的 `track-pi/src/agent.ts` 与 `shared/` 编译进去，只把 `node:crypto` / `fs` / `path` / `os` 换成浏览器替身。所以判定、审计链、确认令牌、幂等回放全是原代码，持久层落在内存里（刷新即清空），不调模型、不连外部反欺诈。

**连不连后端由你决定，不是默认行为**：两个页面开机就跑页内引擎、一个网络请求都不发。要验真进程（磁盘审计、`/live` `/ready`、退出码）时，`cd track-pi && npm start`，然后加 `?live=1` 打开 —— 那时顶栏会写「已连本机进程」。

源码在 `web/public/demo.html`；改完 `agent.ts` 或 `shared/` 后跑 `node scripts/build-demo-engine.mjs` 重新打包（也会同步 `web/dist`），`--check` 只编译并自检不写盘。

**多客户**：演示台顶部可以切换四个客户（林知远、周雅、陈默、苏晚），一人一本账。**姓名互相看得到** —— 转账要核对是转给谁；**金额和账户操作一律看不到**。这不是界面上藏起来：身份由令牌决定（`x-siheng-token`），服务端按令牌只交出这一份，参数里再塞 `actor` / `tier` 一概不看。会话键带用户前缀，同一个会话编号在两个人身上是两个会话；一个客户一个 `Agent`，草稿和待确认的票天然不共享。客户表在 `shared/directory.ts`，生产环境应换成 OIDC 的 `sub` + 客户主数据。

转账是分轮问的：缺对象就问转给谁、缺金额就问转多少，已经给过的那个会被复述出来。补齐之后出的确认卡上写着「收款人 ××，金额 ×× 元」，不点确认不动账。

只说金额不说人（`再转 100 元`）时分两档接，两档都不替用户把人定下来：

- **同一个会话里刚才点过名的人**（哪怕那一笔还挂在确认卡上、没执行）—— 15 分钟内有效，先反问一句「还是转给小王吗」，你答「是」才开卡；答「不是」就重新问，直接说个新名字就当场换人。换会话、换进程都不认这一档。
- **账户里 30 天内真的转出去过的人** —— 补一个默认值直接出卡，卡片上单独占一段写清三件事：收款人不是你这轮说的、我是按哪一笔补的（带上次的金额和多久以前）、要换人该怎么重说。照样要确认。

两档都会过期；改口一说新的对象，上一张卡立刻作废、旧令牌确认不了。

不想开浏览器就直接打接口（JSON-RPC，`POST /rpc`）：

```bash
curl -X POST http://127.0.0.1:18150/rpc -H "content-type: application/json" \
  -d '{"method":"chat","params":["demo","查一下余额"]}'
```

方法：`chat` / `confirm` / `plan` / `cancel` / `state` / `reset` / `audit` / `tamper`；
转人工侧另有 `handoffs` / `handoff.claim` / `handoff.close` / `handoff.sweep`。

探针两个，别合并：`GET /live` 只看进程活着（退出中也照样 200，否则调度会重启一个正在正常退出的进程）；`GET /ready` 看能不能派活 —— 正在退出、状态文件读坏回落初始值、落盘目录写不进去，这三种都返回 503 并写明原因。
发 `SIGTERM` 或按 Ctrl-C 会走优雅退出：停接新请求（503 说明原因）、等在途办完（默认 10 秒，`SHUTDOWN_TIMEOUT_MS` 可改）、办完退 0，办不完记一笔退 1。

`data/state.json` 读不出来时**拒绝启动**（退出码 78），并打印原因和两条出路：备份后删掉重新开始，或确认要带初始值起就设 `ALLOW_STATE_FALLBACK=1`。这样「文件被手改坏」不会再和「全新安装」长得一样。

### 跑不起来时

- `EADDRINUSE :18150` —— 上一个实例没退。`netstat -ano | findstr :18150` 查到 PID 后 `taskkill /PID <pid> /F`；或直接 `PORT=18200 npm start`。
- `Unknown file extension ".ts"` —— Node 低于 22，升级 Node。
- `npm start` 报找不到 package.json —— 没进 `track-pi/`。`cd track-pi` 后再跑，或在根目录 `node track-pi/src/index.ts`。
- 界面空白 —— `web/dist` 缺失。`npm --prefix web install && npm run build:app`（构建后会把 JS/CSS 内联成单文件，`file://` 也能直接打开）。

## 运维：追一笔、看一片、挡一片

判定做得好不好是白天的事，这三件事是半夜的事。

```bash
# 追一笔：每个响应都带 traceId，同一个 id 也在审计与日志里
curl -i -X POST http://127.0.0.1:18150/rpc -H 'content-type: application/json' \
  -d '{"method":"chat","params":["web:1","转给小王 100 元"]}' | grep -i x-trace-id

# 看一片：Prometheus 文本，11 个指标（请求量 / 耗时 / 判定分布 / 确认率 / 幂等命中 / 工单积压 / 限流拒绝 / 链长 / 进程）
curl -s http://127.0.0.1:18150/metrics | head -20

# 挡一片：默认每客户 120 次/分钟、突发 40；超了就是 429 + Retry-After，被拦那次也带 traceId
RATE_LIMIT_PER_MINUTE=12 RATE_LIMIT_BURST=4 npm start
```

- **traceId 用 `AsyncLocalStorage` 传递**，不给 agent.ts 的每个方法加参数 —— 漏传一处就断链，而断链不报错。
  网关带了 `x-trace-id` 就沿用；格式非法的丢弃另造（单行日志，任意字符串进去就能伪造一行）。
- **审计记录里的 `traceId` 参与哈希**，改了会断链；而旧格式（没有这个字段）的记录仍然通过校验 —— 加字段不能把旧账变成坏账。
- **指标只放低基数标签**。`sessionId` / `userId` / `traceId` 绝不进标签，它们只出现在日志里。
- **日志 `LOG_FORMAT=json`** 一行一条，用户原话脱敏后截断 80 字，`LOG_USER_TEXT=off` 可完全不落。
- **限流按客户不按 IP**：配额是给客户的，一个人两部手机是同一份额度。桶会自清，一万个不存在的客户吃不掉内存。

### 账坏了必须被说出来

「审计链完整」这句话本身不保证账没被改过 —— 链能验出「中间被改过」，验不出「尾部被砍掉」；改余额也不必碰审计文件。所以三道独立的闸：

| 坏法 | 谁拦下来 | 拦下来之后 |
|---|---|---|
| 手改 `state.json` 余额 | **状态自摘要**（落盘时算 sha256，读盘时对不上就拒绝启动） | 退出码 78 + 报明「盘上摘要 X…，重算得到 Y…」 |
| 砍掉审计链尾部几行 | **链头锚点** `audit.head`（独立文件，每次追加后重写） | 退出码 78 + 报明「锚点记着链上有 N 条，盘上只有 M 条」 |
| 把幂等 / 工单 / 会话记录改坏 | **丢弃计数 + 旁存留证**（`.rejected-*.json` 带原文与原因） | 丢弃不静默，`health` 里 `rejected` 看得见 |

```bash
curl -s http://127.0.0.1:18150/health | python -c "import json,sys; d=json.load(sys.stdin)['persistence']; print('链头锚点:',d['auditHead']); print('丢弃计数:',d['rejected'])"
```

三条都是**先实测复现、再逐条堵上**的（改坏数据 → 看到旧行为毫无察觉 → 修 → 复验拦住了），
负向验证做了三轮：去掉摘要写入 4 条测试挂、去掉锚点写入 3 条挂、去掉丢弃计数 1 条挂。

保证什么、边界在哪（含**已知且不打算修的 7 条**，比如 TTL 过期、有写权限的攻击者能重算整条链）
见 `docs/10-数据完整性契约.md`。

细节、排障对照表、容器与流水线见 `docs/09-运维手册.md`。

## 这个仓库现在能演示什么

启动包只给了骨架，下面这些是补上去的，全部有实测证据（`node scripts/verify-cases.mjs` 167 条用例）。

- **六个场景全覆盖，赛题子项补到最后两个**：转账（人名/手机号/备注/预约/**拆分 AA 收款**）、账单分析（本月/上月/近三月/今年）、理财操作（货架对比、风险适当性、申购、赎回）、卡片管理（锁定、挂失、额度调整、办卡）、订阅代扣（识别、7 天提醒、取消）、跨场景联动（多步计划/**生日前 2 天自动下单鲜花蛋糕**）。
- **AA 收款按总额判限额，不按人均**：480 元 4 人每人 120 元；500 元 3 人除不尽时零头由发起人承担，收款单三个数相加恒等于总额。按人均判的话拆成 20 个人就能绕过所有限额。
- **生日礼遇是「预锁 → 到期下单」两步**：一句话拆成锁 1000 元 + 登记生日前 2 天 09:00 下单；下单资格来自预锁额度（无锁不下单、超预算不下单），到点扣 458 元、释放 542 元，预锁过期则如实取消。调度器每 60 秒一拍，`tick` 可传时间做确定性验收。
- **会算账，不只是会办事**：说「分期月费率 0.6%、分 12 期、本金 12000 元」，系统给出每期还款 1072.00 元、手续费 864.00 元，以及**真实年化 13.03%**（复利口径 13.84%）—— 名义年费率 7.2% 是它自己算的乘 12，同一个回复里必须同时给出，且要点明「月费率不能直接乘 12 当年化」。真实年化用 IRR 反解（二分法），不用速算近似；参数越界（期数不在 1—60、月费率不在 0—5%）直接拦红，不硬凑一个数。
- **收益不是摆设，是按天真的在长**：持仓记买入时间与已计收益，收益 = 本金 × 年化 × 持有天数 ÷ 365，按**毫分**累计（1 分 = 1000 毫分）—— 一笔 100 元的货币基金一天只赚 0.49 分，不足半分，若每天四舍五入到分，零头天天被抹掉，持有一年就是系统性少算。查询时把「应计未落账」也算进市值，但**不写状态**（查询不改账）；结息只发生在赎回，把应计搬进活期，搬运本身一分不增，不足 1 分的零头记进 `roundingMilliCents` 而不是悄悄抹平。赎回判黄、不可撤销但可确认（金卡以上才可办），这条路径由单测与不变量测试守着。
- **判定不能只看交易形状**：同样 3 笔、每笔 54 元、收款人各异的两批转账，形状读数（笔数、每笔、合计、笔间极差、与限额的关系）一字不差；差别全在证据 —— `aml_check` 逐项核对 AA 收款单、收款人是否在册、有没有能覆盖本批金额的消费，且**一笔消费只能解释一次分摊**。三项证据齐全也只判黄（补凭证后人工放行），证据不足判红、线上不执行。「读懂意图就放行」不是可解释 AI，那是 AI 自我批准。
- **四十四条判定规则**：`self-transfer`（收款人是本人，转账不成立）、`tool-whitelist`、`base-level`、`actor-tier`、`tier-insufficient`、`grounding`、`irreversible`、`payee-from-remark`、`payee-from-card-number`、`external-risk`、`external-degraded`、`single-limit`、`daily-limit`、`midnight-burst`、`new-payee`、`reversibility`、`frequency`、`suitability`、`min-amount`、`split-headcount`、`split-share`、`split-limit`、`split-daily`、`split-outsider`、`gift-no-date`、`gift-lead`、`gift-items`、`gift-no-lock`、`gift-over-budget`、`gift-lock-pending`、`gift-budget`、`installment-quote`、`installment-nominal`、`installment-misleading`、`installment-invalid`、`aml-shape`、`aml-structuring`、`aml-hugging`、`aml-not-split`、`aml-record`、`aml-relationship`、`aml-purpose`、`aml-explained`、`aml-evidence-gap`。每条都有独立 rule 名与含具体数字的 detail，界面最多显示两行。
- **权限分级是二维的**：主体档位（普通/金卡/私行）× 操作风险。同一句「转给小王 800 元」，普通客户判红、金卡客户判黄，判定里写明按哪个档位判的。
- **任务规划与回滚**：一句话里有两件事会被拆成多步（`先查一下余额，然后把云端音乐取消`），每步单独判定与留痕；任一步判红或执行失败则整链停下，并把能撤的按逆序撤回去 —— 撤不掉的（转账、取消订阅）如实说明，不返回假成功。
- **幻觉防护**：模型给出的金额与收款人必须能在原文或通讯录里找到依据，找不到就判红（`grounding`），不给"模型编一个收款人"留口子。
- **确认时重算**：发令牌到用户点确认之间状态若已变化，按确认时的状态重判，升级成红就停手。
- **重试不重做**：`chat` 与 `confirm` 接受 `requestId`，同一个编号只执行一次。票是一次性的、核销即废；用户超时再点，按编号回放首次结果而不是「没有待确认的操作」。同一个编号换了内容直接拒（判误用，不执行也不回放）。记录落 `idempotency.json`，三态 `inflight / done / failed`：**`inflight` 先落盘**，崩在执行中间重启后如实答「结果未知，已转人工核对」，绝不闷头再转一笔。不带编号的请求原样穿过，行为与 1.7 一致。
- **转人工真的转出去**：上面那句「已转人工核对」在 1.11.0 之前只是七个字。现在开一张工单（`shared/handoff.ts`，落 `handoff.json`）：交接包带原话、幂等编号、审计序号、已做动作、建议确认项，缺一个字段就开不出单；人工侧走 `handoffs` / `handoff.claim` / `handoff.close` 认领与结案，重复结案拒绝，结论必须是 `released / confirmed / rejected / no-action` 之一。悬空金额写 `null` 不写 `0` —— 崩溃场景里「不知道动了多少」是常态，写 0 会让人以为没悬空。**转人工的原因有准入条件**：钱没动就不许按「悬空资金」开单、工具能线上办就不许按「必须柜面」开单，于是不该转的路径根本产生不了工单。
- **外部服务两路**：汇率换算与反欺诈筛查都走 stdio JSON-RPC，3 秒超时。反欺诈结论进判定（高→红 / 中→黄 / 低→记一条），服务挂了降级为需确认并写明哪条链路不通；服务挂掉时内置工具照常可用。
- **渠道**：Web 前端与通用 webhook，支持 HMAC 验签；webhook 层另有一层**进程内**去重（平台给了 `messageId` 就用它，否则按「用户 + 文本」兜底），只挡平台重发，重启即失效，也不覆盖 Web 端。真正的执行级幂等在上面那条 `requestId` 上，两者是两层而不是一层。
- **一笔能追到底、一片能看出好坏、刷子挡得住**：每个请求带 `x-trace-id`（网关带了就沿用），同一个 id 同时出现在响应头、审计记录（参与哈希，改了断链）与 JSON 日志三处 —— 用户说的那句话、审计里那条记录、日志那几行能对上；`/metrics` 出 11 个指标（Prometheus 文本），默认只认回环、跨机要 `METRICS_TOKEN`；按客户的令牌桶限流，超了 429 + `Retry-After`，**被拦的那次也带 traceId**。容器两阶段构建、非 root、只读根 + 数据卷 + `HEALTHCHECK`；CI 串起五套已有验证并真起一次镜像发一次对话。
- **审计可校验、可演示**：哈希链逐条串联，记操作主体；`DEMO_TAMPER=on` 时可现场改一条，链立刻断在那一位置。
- **账被改坏了会被说出来，而且说得清是哪一种坏**：哈希链能验出「中间被改过」，验不出「尾部被砍掉」；改余额也不必碰审计文件 —— 所以另有三道独立的闸：**状态自摘要**（手改 `state.json` 余额 → 读盘对不上 sha256 → 拒绝启动）、**链头锚点** `audit.head`（独立文件，砍审计尾巴 → 报「锚点记着 N 条，盘上只有 M 条」）、**丢弃计数 + 旁存留证**（幂等/工单/会话记录坏了 → 不静默丢掉，落 `.rejected-*.json` 带原文与原因，`health` 的 `rejected` 看得见）。三条都是**先实测复现、再逐条堵上**的 —— 改坏数据看到旧行为毫无察觉，修完复验确实拦住了。保证什么、边界在哪（含 7 条已知不修）见 `docs/10-数据完整性契约.md`。
- **落盘与重启**：审计追加写 JSONL（逐行 fsync），状态与会话原子写；杀掉进程重起后审计、余额、待确认令牌、日累计都还在。`PERSIST=off` 可退回纯内存。
- **账务日口径**：日累计按业务时区与账务日切分点统计（`BIZ_TZ_OFFSET_MIN` / `ACCOUNT_DAY_CUTOFF`），并补了跨账务日连笔规则（`midnight-burst`）。
- **资产守恒是机证的，不是人查的**：`scripts/invariants.test.mjs` 不断言某个用例的结果，而是先声明三条恒等式 —— 账面减可用恒等于预锁合计、净资产变化必须恰好等于这一步真实的资金流出、被拒的操作前后状态逐字节相同 —— 再用 120 步随机操作序列（固定种子，失败可原样重跑）去撞。负向验证证明它有牙齿：把转账改成只扣账面不扣可用，第 2 步就报「账面与可用之差应等于预锁合计」；把计息基准 365 写成 36.5，一年利息 166600 分立刻越过独立算出的上限 59062 分。
- **账单真实口径**：商户名归一（分支括号、`-旗舰店` 后缀、中英混排）、MCC 码分类、退款冲正；异常按同类其他交易的中位数判，回复里写出基准与倍数。
- **四个可能被问住的设计取舍，主动说在前面**：
  - **红色为什么不设「验证通过后继续办」的第三态** —— 任何「验证后放行」的通道都是一条绕过路径，其安全性取决于验证环节；本系统没有真实身份验证基础设施（无短信网关、无人脸核身），**在演示环境里模拟一个假验证比不提供这条路径更危险**。红色也不等于「拒绝服务」，而是转人工或柜面并给出明确指引（`handoff` 的 `manual-only` 理由，工单带原话、幂等编号、建议确认项）。赛题原文第三条只写「权限分级机制」，没有写「红色 = 强验证」。
  - **没有代码沙箱，因为没有可沙箱的客体** —— 系统里不存在代码解释器，也不存在 `eval` 一类的动态执行点：模型只产意图，能落地的动作全是 `shared/rules.ts` 里的确定性工具，参数须过「工具白名单 → 类型与范围 → 意图双向溯源（groundIntent）」三重闸。等效隔离由四件事提供：**执行面封闭**（工具是有限枚举，不是任意函数调用）、**参数校验**、**副作用前置于校验**（判定与取证都在写状态之前，不存在「先执行后校验」的窗口）、**全程哈希链留痕**。不是把代码关进笼子，是根本不给代码开口子。
  - **计划是线性链而非分支 DAG** —— 条件落在每一步内部的前置守卫上（如「余额足够才转账」的 `balance-sufficient` 守卫），不落在图的拓扑上。分支意味着某步可能执行也可能不执行，「执行了哪些」就得靠运行时留痕；线性链换来**每步判定与顺序无关、回滚是确定的逆序 undo、整链一次授权**。代价如实说：真正需要改道的场景退回「转人工 + 保留已做动作」，不自动改道 —— 金融场景里「钱到底动了几笔」比「自动多试一次」更重要。
  - **两条真实缺口，如实登记在 `docs/` 与技术文档 §8** —— ① **账户级安全锁定未做**：现有多维风控（频次超限、拆分形态、外部风控高危）只「拒这一笔」，没有「锁住账户」的状态；限流是配额双桶、属防刷不是熔断。补法是加账户级锁定态 + 累计触发规则 + 人工解锁路径，要碰状态层与规则计数。② **执行中不可主动中止**：整链执行期间不可打断，`cancel` 只能撤「待确认」态；当前以「整链失败自动逆序回滚 + 如实告知哪步撤不掉」替代，因为半执行链的账目归属比即时中止更难说清。

运行方式、接口、校验命令与常见报错见上面的「怎么跑起来」。三分钟演示跑稿见 `scripts/demo.mjs` 与 `演示脚本.md`，交付自述见 `自述.md`。

一句话：两条可魔改的 Agent 框架路线，加一套完整的工程配套，帮你在三天内交出一个能演示、能评审、能答辩的银行智能体项目。

## 这个包解决什么问题

大部分同学卡在三个地方。

一是不知从哪下手。赛题给了六个场景、三条门槛，但没有给起点。

二是框架选不明白。有人推荐插件化的重型框架，有人推荐单文件循环，两种说法都对，但混在一起就无从下手。

三是工程配套缺失。只写了一个对话接口，没有子代理分工、没有评审清单、没有版本管理、没有渠道接入，答辩时无法证明「这是完整软件工程」。

这个包把三件事一次解决：两条路线的可运行骨架、一套子代理与评审流程、一批开箱即用的技能与外部服务。

两条路线共用前端、技能、外部服务与渠道适配，差异在运行时编排层。

两条路线都能通过赛题的三条门槛，选哪条只取决于团队规模与时间。

## 边界声明

这个包不含任何真实的银行接口，所有账户、账单、产品都是合成数据。

外部服务里的汇率、征信、费率是演示值，不能用于真实业务。

包里的安全设计参考了生产实践，但不构成合规认证。

运维这一层也是**单副本形态**：指标与限流都在进程内存里，多副本时各报各的、各算各的。
账本写盘有版本校验与写锁，会话 / 幂等 / 工单三份登记簿改成**加锁 + 合并写**，
两个写者各写一份不再互相抹掉（v1.18.6）。剩下的边界写在 `docs/09-运维手册.md`
的「已知边界」里，不藏着。
