# 数据完整性契约

这份文档说清一件事：**这份账上，哪些东西丢了会被发现，丢了会怎样，以及发现不了的地方在哪。**

写它的理由不是文档洁癖。数据完整性最怕的不是"有 bug"，而是**静默地丢东西** ——
丢了没人知道，等发现时已经晚了，而且往往说不清是哪一笔丢的。

每一条都写明三件事：**保证什么、怎么保证、边界在哪**。
边界必须写：一份只写好处的完整性说明，比没有说明更危险 ——
它会让评审以为所有坏情况都覆盖了。

---

## 一、盘上有什么

| 文件 | 位置 | 内容 | 写入方式 |
|---|---|---|---|
| `audit.jsonl` | `DATA_DIR/`（全局单链） | 审计记录，哈希链 | 追加写，每行 fsync |
| `state.json` | `DATA_DIR/users/<userId>/` | 账本状态 | 原子写（临时文件 → rename） |
| `sessions.json` | 同上 | 会话快照（含墓碑） | 登记簿式写入 |
| `idempotency.json` | 同上 | 幂等日志 | 登记簿式写入 |
| `handoff.json` | 同上 | 转人工工单簿 | 登记簿式写入 |

## 二、五条保证

### 保证 1：审计链能查出「中间被改过」

**保证什么**：审计链上任意一条记录的内容被改动，`chain.ok` 会变成 `false`，
并指出断在第几条（`brokenAt`）。

**怎么保证**：每条记录带 `prevHash`（前一条的哈希）与 `hash`（本条的哈希）。
哈希算的是 `sha256(prevHash | 记录正文)`，正文含 seq、sessionId、actor、userText、
tool、decision、level、rules、result、traceId。

改一条记录 → 它的 `hash` 与重算值不符 → 断链；即使把 `hash` 一起改对，
`prevHash` 也会与上一条的 `hash` 对不上 → 仍然断。

**边界**：这条保证只覆盖**中间**。尾部被整行删掉时，剩下的记录依然自洽，
链校验通过 —— 见保证 2。

---

### 保证 2：审计链能查出「尾部被截断」

**保证什么**：审计文件最后若干行被整行删掉（不是改内容，是删行），
系统会发现，并且**不会**在缺口处悄悄接着写。

**怎么保证**：**链头锚点**（`audit.head`）。

每次追加审计记录后，把「链头」的三个值写进一个独立的小文件：
- `seq`：链头的序号
- `hash`：链头的哈希
- `count`：链上总条数

启动时读这个锚点，与盘上审计文件的实际链头比对：

| 情况 | 判定 | 处理 |
|---|---|---|
| 锚点 `count` > 盘上条数 | **尾部被截断** | 拒绝启动，报明缺了多少条 |
| 锚点 `count` == 盘上条数，`hash` 不符 | 链头被改 | 拒绝启动 |
| 锚点 `seq` 与盘上最后一条 `seq` 不一致 | 序号重号 | 拒绝启动 |
| 锚点缺失（首次运行） | 正常 | 建立锚点 |

**为什么锚点要单独一个文件**：放在审计文件里等于没放 ——
删尾巴的人会连锚点一起删。放在**另一个文件**里，
删审计尾巴而忘了锚点就会被发现。这是「多一处独立证据」的思路。

**为什么拒绝启动而不是打个警告**：审计链是「发生过什么」的唯一证据。
证据不全却继续开门，等于假装还查得出真相。停住让人看，比给一份看起来完整的
假记录更安全。

**边界**：锚点文件本身也能被改。这是本地文件系统的固有上限 ——
拿到写权限的人可以同时改审计和锚点，把整条链重算一遍。
本项目**不声称**能防住有写权限的攻击者，只声称能防住：
意外截断、误删、部分篡改、以及「忘了改第二个文件」的攻击。
要防住有写权限的攻击者，需要的是签名密钥或外部锚定，不在本项目范围内。

---

### 保证 3：手改 `state.json` 的余额会被查出

**保证什么**：有人直接编辑 `state.json` 把 `account.balance` 改成另一个数，
系统会发现并拒绝启动。

**怎么保证**：**状态自摘要**（`state.json` 里的 `integrity` 字段）。

写盘时，除了账目本身，额外写一个 `integrity` 字段：
```
integrity = { algo: "sha256", digest: <对账目正文的摘要>, seq: <写入时的 revision> }
```
摘要算的是**去掉 integrity 字段本身之后**的整个状态对象的规范化 JSON。
读盘时重算一遍，对不上就是「这份状态在落盘之后被改过」。

**为什么不用审计链做交叉校验**：审计记录里没有结构化的金额字段
（金额混在 `result` 自然语言里），从自然语言反解金额去做对账不可靠 ——
解错一次就会误报，而误报会让人不再相信这个信号。
状态自摘要不需要解析任何东西，**改一个字节就一定对不上**。

**为什么摘要是自包含的（不带密钥）**：带密钥的摘要需要一个双方共享的秘密，
存在哪里本身就是新问题。本地演示项目里没有密钥体系，
自摘要的定位是「**误改必被发现**」，不是「防住有密钥的攻击者」——
和保证 2 的边界是同一条。

**边界**：同样挡不住「改完账本后重算摘要」的有心人。
但它挡得住绝大多数真实场景：手滑改错、脚本批量改、编辑器误存、
拷贝了另一份 state.json 过来。

---

### 保证 4：坏数据条目不会被静默丢弃

**保证什么**：登记簿里某一条记录字段坏了（缺字段、类型不对），
这一条会被**计数并留证**，而不是无声无息地消失。

**怎么保证**：每个 merge 函数返回一个「丢弃统计」，
被丢弃的条目原文写进**旁存文件**（`.rejected-<时间戳>.json`），
并计入 `health` 的 `rejected` 读数。

涉及四个 merge 函数：
- `mergeSessionsSnapshot`（会话）
- `mergeIdempotencySnapshot`（幂等）
- `mergeHandoffSnapshot`（工单）
- 审计装载时的 `isAuditRecord` 过滤

**为什么留证是必须的**：丢弃是永久的（合并结果会覆盖原文件），
不留证就等于「这里本来有一份东西」这个事实永远消失。
留一份原文在旁边，事后至少能查清丢的是什么。

**边界**：被丢弃的条目仍然会丢（不并进正式数据）——
因为一条字段坏掉的记录并进去，可能让系统误判「这笔已经办过了」。
**丢掉并留证**比**留着并当真**安全。
这一点在幂等日志上尤其重要：一条半坏的幂等记录会让系统以为某笔请求已经办过，
那是错的方向。

---

### 保证 5：坏文件不删、不覆盖、旁存留证

**保证什么**：`state.json` / `sessions.json` / `idempotency.json` / `handoff.json`
如果整体读不出来（不是合法 JSON），原文件会被**改名保留**（`.bad-<时间戳>`），
新数据写到新文件。

**怎么保证**：写路径上的 `preserveBad()`。读路径上，
`state.json` 的损坏会**拒绝启动**（退出码 78），
其余三个文件的损坏会在下次写入时旁存留证。

**为什么 state.json 严一档**：它是余额。拿初始余额冒充用户的钱比停住更危险。
其余三个文件坏掉，丢的是会话上下文、幂等记录、工单 —— 影响可控，
但仍然必须留证，因为它们坏掉的后果同样不可逆。

## 三、审计链装载时「坏记录」的三种命运

审计文件是 JSONL，一行一条。启动时逐行处理：

| 行的状态 | 处理 | 是否计入 `corruptLines` |
|---|---|---|
| 不是合法 JSON | 跳过 | 是 |
| JSON 合法但字段不全（缺 `actor` 等） | 跳过 + **留证 + 计数** | 是（新增口径） |
| 字段完整 | 进链 | 否 |

第二类以前是**静默丢弃** —— 字段不全的行被 `isAuditRecord` 过滤掉，
不留证、不计数、不告警。
现在它和第一类一样计入 `corruptLines`，并把原文写进旁存文件。

**为什么单独拎出来说**：这两类都是「数据坏了」，
但以前只有一类会被发现。审计链在中间断了能查出来，
**在尾部断了查不出来** —— 而尾部那一条恰恰可能是被单独改坏的那条。
所以「尾部被改坏」必须靠保证 2 的锚点来查，不能指望链自己。

## 四、已知且不打算修的

诚实列出来比藏着好。评委问起来，「这个我们想过，原因是 X」比「啊这个吗」强。

| 问题 | 为什么现在不修 | 会造成什么 |
|---|---|---|
| 有写权限的攻击者可重算整条审计链 | 需要签名密钥或外部锚定，本项目无密钥体系 | 审计链对「有盘上写权限的人」不构成对抗性保护 |
| 幂等记录 TTL（30 分钟）过期后同一 requestId 会重做 | 是文档化的设计取舍：「超时后可以再用」 | 31 分钟后重发同一笔转账会再执行一次 |
| `inflight` 幂等记录也受 TTL 约束 | 同上 | 崩溃超 30 分钟后，「结果未知」信号消失，系统会闷头重做 |
| 审计记录里没有结构化金额 | 补它要改哈希链的正文，会让所有历史记录的哈希失效 | 无法从审计链独立重算余额做对账，故保证 3 用状态自摘要而非链上对账 |
| `dropAudit()` 无鉴权 | 当前零调用方，未暴露在任何 RPC 入口 | 理论风险；接进 per-user 入口会抹掉全局单链 |
| 只读读数与业务请求共用一个令牌桶 | v1.19.0 已分离（只读 6 倍配额） | 已修 |

## 五、怎么自己验

```bash
# 1. 结构自检（含本契约涉及的必存在文件）
node scripts/check.mjs

# 2. 数据完整性专项测试
node --test scripts/integrity.test.mjs

# 3. 手工验「尾部截断会被查出」：
#    起服务 → 转一笔账 → 记下 health 的 chain.count
#    → 删掉 audit.jsonl 最后一行 → 重启 → 服务应拒绝启动并报明缺了几条
```

每一条保证都有对应的回归测试，见 `scripts/integrity.test.mjs`。
**没有测试的保证不算保证** —— 改代码的人会把它改坏，
而改坏的时候不会有任何报错提示。
