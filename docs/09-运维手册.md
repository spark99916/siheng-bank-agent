# 09 运维手册：追一笔、看一片、挡一片

这篇不讲设计，只讲**半夜被叫起来的时候手上有哪些东西、按什么顺序用**。

前提：服务用 `cd track-pi && npm start` 起来，默认 `127.0.0.1:18150`。
下文所有命令都在本机执行；容器里的把地址换成容器名即可。

---

## 一、先分清三件东西

| 出什么问题 | 用哪个 | 一句话 |
|---|---|---|
| 「这用户说他转了一笔，账上没扣」 | **traceId** | 把他那句话、审计那条记录、日志那几行串起来 |
| 「现在服务好不好」 | **`/metrics`** | 请求量、耗时、判定分布、拒绝率 |
| 「有人在刷接口」 | **限流 + 429 计数** | 按客户令牌桶，超了就说「几秒后再来」 |

三样都不进业务层：`agent.ts` 一行没改。判定只做判定，运维是入口的事。

---

## 二、追一笔：traceId 怎么用

### 它从哪来

每个请求进门生成一个 16 位十六进制，**在响应头里回给你**：

```bash
curl -i -X POST http://127.0.0.1:18150/rpc \
  -H 'content-type: application/json' \
  -d '{"method":"chat","params":["web:1","转给小王 100 元"]}' | grep -i x-trace-id
# x-trace-id: 08aae4fea38b4c48
```

网关（或渠道适配层）已经生成的话，**带 `x-trace-id` 进来就沿用它的**：

```bash
curl -i -X POST http://127.0.0.1:18150/rpc \
  -H 'content-type: application/json' \
  -H 'x-trace-id: gw-20261101-0001' \
  -d '{"method":"state","params":[]}' | grep -i x-trace-id
# x-trace-id: gw-20261101-0001
```

一条链路只有一个 id。中间再生成一次，等于把「跨服务追一笔」这件事做废。

格式不合法的（少于 8 位、超过 64 位、带空格或换行）**会被丢弃另造** ——
日志是单行文本，任意字符串进去就能伪造一整行日志。

### 它在哪三个地方同时出现

1. **响应头**：客户端侧能立刻记下来
2. **审计记录**：`audit.jsonl` 里每行的 `traceId` 字段（参与哈希，改了会断链）
3. **日志**：`LOG_FORMAT=json` 时每行的 `traceId`

### 实操：用一句话找到那条审计

```bash
# 1. 发一句话，记下 traceId
TRACE=$(curl -s -D - -o /dev/null -X POST http://127.0.0.1:18150/rpc \
  -H 'content-type: application/json' \
  -d '{"method":"chat","params":["web:2","转给小王 100 元"]}' \
  | grep -i x-trace-id | tr -d '\r' | cut -d' ' -f2)

# 2. 在日志里找这次请求
grep "$TRACE" logs/*.jsonl | head

# 3. 在审计链里找那条记录
grep "$TRACE" data/audit.jsonl
```

三条记录里的 `seq`、`userText`、`level` 应该是同一件事的三个视角。
对不上就是有问题 —— 而这正是「能追」的意义。

## 三、看一片：`/metrics` 怎么读

```bash
curl -s http://127.0.0.1:18150/metrics
```

### 指标清单

| 指标 | 类型 | 回答什么问题 |
|---|---|---|
| `siheng_rpc_requests_total{method,status}` | counter | 谁在打、打成什么样 |
| `siheng_rpc_duration_ms{method}` | histogram | 慢在哪一步，P99 多少 |
| `siheng_decisions_total{level}` | counter | 判绿/黄/红的比例 |
| `siheng_confirm_total{outcome}` | counter | 确认卡签出去多少、办成多少 |
| `siheng_idempotency_total{kind}` | counter | 重放、中断、冲突各几次 |
| `siheng_llm_tokens_total{kind}` | counter | 模型花掉多少 token |
| `siheng_handoff_open{state}` | gauge | 人工工单积压 |
| `siheng_ratelimit_rejected_total{scope}` | counter | 被挡了多少次 |
| `siheng_audit_chain_length` | gauge | 链上多少条 |
| `siheng_process_uptime_seconds` / `_rss_bytes` | gauge | 进程状态 |
| `siheng_ready` | gauge | 1 就绪 / 0 未就绪 |

**卡号和姓名不在指标里**。`sessionId`、`userId`、`traceId` **也不进标签** ——
那是高基数，会把时序库撑爆。它们只出现在日志里。

### 三个立刻能用的判读

**P99 耗时**：`siheng_rpc_duration_ms` 的 `le="2500"` 那个桶。
如果 `+Inf` 减 `le="2500"` 还有明显数量，说明有请求超过 2.5 秒 —— 那基本是在等模型。

**判定分布**：`siheng_decisions_total{level="red"}` 突然飙升，先看是业务变了还是规则错了。
判红多不一定是坏事（风控起作用了），但**红的占比一天之内翻倍**值得查。

**确认转化率**：`siheng_confirm_total{outcome="executed"}` ÷ `siheng_decisions_total{level="yellow"}`。
这个比值长期低于 0.5，说明用户签了卡又不确认 —— 要么文案吓人，要么在别的设备上忘了。

### 抓取权限

默认**只认回环**（`127.0.0.1` / `::1` / 同 pod sidecar）。
监控系统从别的机器抓，必须设 `METRICS_TOKEN` 并带 Bearer：

```bash
METRICS_TOKEN=s3cret npm start
curl -s -H 'authorization: Bearer s3cret' http://127.0.0.1:18150/metrics
```

指标里虽然不含金额和姓名，但请求量、拒绝率、工单积压本身就是攻击者的地图。

### 不想装 Prometheus 的时候

```bash
curl -s 'http://127.0.0.1:18150/metrics?format=json' | head -c 800
```

同一份数据，JSON 视图。答辩现场用浏览器看一眼够用。

## 四、日志怎么接

```bash
LOG_FORMAT=json LOG_LEVEL=info npm start
```

一行一条，字段固定：

```json
{"status":200,"latencyMs":12.9,"ts":"2026-11-01T13:50:30.045Z","level":"info","event":"rpc",
 "traceId":"1e821722081749c2","method":"chat","userId":"u-1001","sessionId":"u-1001:web:t1","elapsedMs":13}
```

常用事件：

| `event` | 什么时候 | 关键字段 |
|---|---|---|
| `chat` | 每次对话 | `scene`、`decision`（绿/黄/红）、`rules`、`auditSeq`、`loopSteps`、`userText` |
| `rpc` | 每个 RPC 请求结束时 | `status`、`latencyMs` |
| `confirm` | 确认动作 | `decision`、`executed` |
| `ratelimit.rejected` | 被限流 | `userId`、`retryAfterMs` |
| `auth.rejected` | 令牌换不出客户 | `tokenPresent` |
| `metrics.rejected` | 抓指标没带令牌 | `remote` |

三条硬规矩：

1. **级别不会被业务字段覆盖**。业务里有个字段也叫 `level` 也改不掉 —— 保留字段最后写。
2. **令牌类字段一律丢弃**（`token` / `authorization` / `cookie` / `apiKey`）。写进代码也不会出去。
3. **用户原话脱敏后截断 80 字**；`LOG_USER_TEXT=off` 完全不落。
   银行环境默认该关，演示环境开着能对上账。

## 五、挡一片：限流怎么配

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `RATE_LIMIT_PER_MINUTE` | 120 | 每客户每分钟次数，**设 0 关闭** |
| `RATE_LIMIT_BURST` | 配额的 1/3（最少 5） | 突发容量 |

为什么按客户而不是按 IP：配额是给客户的。一个人从手机和电脑同时发，是同一个人的两份额度。

为什么是令牌桶而不是固定窗口：固定窗口在边界上有两倍突发（59 秒来 60 次、61 秒再来 60 次），
而边界突发正是最该拦的形态。

超限返回：

```
HTTP/1.1 429 Too Many Requests
retry-after: 5
x-trace-id: 7dc3b148c0644b18

{"ok":false,"error":"请求太频繁：每个客户每分钟 12 次，请 5 秒后再试"}
```

被限流的那次也带 traceId —— 不然运维只能看到「有人被挡了」，看不到「谁被挡了」。

判序：**认证 → 限流 → 建 Agent**。被拦的请求不碰磁盘、不建对象、不占内存。

## 六、容器怎么起

```bash
docker build -t siheng:latest .
docker run --rm -p 18150:18150 --read-only --tmpfs /tmp \
  -v siheng-data:/app/data siheng:latest
```

或者：

```bash
docker compose up -d --build
docker compose exec siheng wget -qO- http://127.0.0.1:18150/metrics | head
```

镜像里刻意做的四件事：

| 做法 | 为什么 |
|---|---|
| 非 root（uid 10001） | 拿到命令执行也改不了系统 |
| `--read-only` + `tmpfs /tmp` | 只能写数据卷，改不了代码、留不下后门 |
| `HEALTHCHECK` 接 `/live` | 健康检查失败会重启；`/ready` 失败该做的是摘流量，不是重启 |
| `HOST=0.0.0.0` 只在镜像里设 | 开发机上默认对外监听不是「方便」，是事故来源 |

容器里唯一可写的地方是 `/app/data`。这也意味着：**换成只读根之后，任何「顺手写个临时文件」的代码都会现形**。

## 七、出事怎么办：症状 → 先看哪

| 症状 | 先看 | 多半是什么 |
|---|---|---|
| 探针 503，reason 是「状态文件存在但读不出来」 | `/ready` 的 `checks.stateOrigin` | 状态文件被手改或写盘断电。**不要直接删**，先备份 |
| 探针 503，reason 是「落盘目录不可写」 | `checks.persistence.writable` | 卷没挂上 / 权限不对（容器里是 uid 10001） |
| 探针 503，reason 是「正在退出」 | `checks.phase` | 收到 SIGTERM 在 draining，正常现象 |
| 用户说转了但没扣 | 用 traceId 串审计与日志 | 多半是卡在「需确认」没点；`level=yellow` 且没有 `confirm` 日志 |
| 429 变多 | `siheng_ratelimit_rejected_total` | 真有人在刷，或者前端把同一个请求重试放大了 |
| 判红变多 | `siheng_decisions_total{level="red"}` + 审计 `rules` | 规则命中了新形态；先看是哪条规则，别急着放宽 |
| 慢 | `siheng_rpc_duration_ms` 的 `le` 分布 | 超过 2.5 秒的基本在等模型；看 `loopSteps` 与 token |
| 内存一路上涨 | `siheng_process_rss_bytes` + `MAX_CACHED_AGENTS` | 冷账户缓存上限（默认 200）；被淘汰的会从盘上重载，账不会少 |
| 审计链断裂 | `/health` 的 `persistence.chain.brokenAt` | 启动时就算过一次；断裂点之前的那条被人改过 |

## 八、已知边界

写在这里，是因为「知道自己差在哪」比「假装没有」有用。

1. **指标只在进程内存里**。多副本时每个实例各报各的，要合并靠 Prometheus 的 `sum by`。
   存储侧已经不是「整份覆盖」了：账本有版本校验 + 写锁，会话 / 幂等 / 工单三份
   登记簿是加锁 + 合并写（v1.18.6），两个写者各写一份不再互相抹掉。
   剩下的多副本缺口在**审计链**：它是追加写 JSONL，没有跨实例的序号协调与写锁，
   多进程同时写同一条链仍可能交错。
2. **traceId 不落进幂等记录**，只在审计与日志里。跨重启追一笔要靠审计 `seq` + 时间。
3. **没有分布式追踪、没有采样、没有告警规则**。指标是原料，规则得按真实业务定 ——
   我编出来的阈值只会误导人。
4. **限流是单机内存的**。多副本时每个实例各算各的，真实总量是「副本数 × 配额」。
   要精确配额得换共享计数器（Redis），那是多实例那一半的活。
5. **Dockerfile 未在本机构建验证**（开发机没装 Docker），由 CI 的 `image` job 负责真跑一遍。
