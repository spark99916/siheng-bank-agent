# 架构与分层

两条路线共用同一套分层，差异只在第四层怎么装配。

## 五层结构

```
第一层  入口      前端页面 / IM 渠道
第二层  协议      HTTP 或 webhook，统一成内部请求
第三层  编排      意图解析 → 判定 → 确认 → 执行 → 审计
第四层  装配      Cordis 插件 或 pi 三段式
第五层  能力      工具、外部服务、技能、状态
```

分层规矩：只能上层调下层，不许下层反向调上层。第五层不知道有 HTTP，第三层不知道插件怎么写。

## 请求怎么走

一次对话走完六段，每段都可单测。

```
用户说：转给小王 500 元
  ↓ 输入守卫：归一化、注入特征
  ↓ 意图解析：落到 transfer，槽位 payee=小王 amountCents=50000
  ↓ 策略判定：黄，需确认
  ↓ 签发令牌：绑定会话、工具、参数摘要、有效期
  ↓ 执行：确认后扣账，写审计
  ↓ 渲染：数字全部来自工具返回
```

每段都有明确输入输出，接口写在 `docs/03` 的契约表里。

## 接口契约

两条路线的运行时都必须实现这五个接口，名称固定。

| 接口 | 输入 | 输出 |
|---|---|---|
| `chat(sessionId, text)` | 会话标识、用户原话 | 回复、判定、可选确认令牌 |
| `confirm(sessionId, token)` | 会话标识、令牌 | 执行结果或拒绝原因 |
| `cancel(sessionId)` | 会话标识 | 取消结果 |
| `state()` | 无 | 账户、卡片、订阅、持仓快照 |
| `audit(sessionId?, limit?)` | 可选会话、条数 | 审计记录与链校验结果 |

前端只认这五个。换路线不用改前端。

## 数据模型

金额一律整数分，不用浮点。这条不商量，浮点在金额上必然出错。

```ts
interface Account {
  holder: string
  balance: number      // 分
  available: number    // 分，扣掉预锁
}

interface Intent {
  scene: string        // 六个场景之一
  tool: string         // 工具名
  slots: Record<string, unknown>
  missing: string[]    // 缺的槽位，非空就追问
  confidence: number
}

interface Decision {
  level: "green" | "yellow" | "red"
  blocked: boolean
  requiresConfirm: boolean
  hits: Array<{ rule: string; detail: string }>
}
```

## 三条不可让的能力

无论选哪条路线，这三样必须在代码里，不能只在文档里。

**三色判定。** 判定要能解释：为什么黄，命中哪条规则。黑盒判定等于没有判定。

### 判定规则表（与 `shared/rules.ts` 的 `evaluate` 一致）

判定只读 `BankState`，不写任何字段；写状态只发生在工具执行里。

判定的第一维度是**主体**，第二维度才是**操作**：`evaluate(intent, state, { actor, ...阈值覆盖 })`，档位由 `actor.tier` 从 `TIER_POLICY` 取，主体没传就按普通客户。

| rule | 触发条件 | 结果 | detail 里的数字 |
|---|---|---|---|
| `tool-whitelist` | 工具不在 `SPECS` 里 | 红·拦截 | 工具名 |
| `base-level` | 总是第一条 | 取工具基础等级 | 工具名、基础颜色、可撤销性 |
| `actor-tier` | 总是第二条 | 不改等级 | 档位名 + 主体 id + 该档位的三条阈值（转账）/ 档位校验说明（其他） |
| `tier-insufficient` | 档位低于 `SPECS.minTier` | 红·拦截 | 当前第几档、需要第几档 |
| `grounding` | 模型给的金额/收款人无法在原文或通讯录溯源 | 红·拦截 | 模型给的数 vs 原文实际的数 |
| `irreversible` | 工具声明 `irreversible` | 红·拦截 | 涉及金额（有金额时） |
| `payee-from-remark` | 收款人来自备注文本 | 红·拦截 | 通讯录人数 |
| `payee-from-card-number` | 收款人写的是卡号 | 红·拦截 | 掩码卡号（前四后四） |
| `single-limit` | 转账金额 > 该档位单笔限额 | 红·拦截 | 本次金额、限额、超出额 |
| `daily-limit` | 当日累计 + 本次 > 该档位日累计限额 | 红·拦截 | 今日已转、本次、合计、限额 |
| `new-payee` | 收款人不在 `transferLog` 里 | 达到该档位红线判红，未达抬黄 | 本次金额、红线、是否在通讯录 |
| `reversibility` | 工具不可撤销但仍允许确认 | 抬到黄 | 涉及金额 |
| `frequency` | 窗口内同一收款人已达该档位笔数上限 | 红·拦截 | 窗口、笔数、上限 |
| `suitability` | 产品风险等级 > 客户承受等级 | 红·拦截 | 产品等级、客户等级、两边标签 |
| `min-amount` | 申购金额 < 产品起购 | 红·拦截 | 起购金额、本次金额 |

阈值分两层：`TIER_POLICY` 是档位矩阵（普通/金卡/私行各一套），`DEFAULT_RISK_POLICY` 等于普通档。`track-pi/src/index.ts` 装配时**只传 `confirmTtlSeconds`，不传阈值** —— 传了就会把档位默认值覆盖掉，这是实测踩过的坑。单次请求可以用第三、四个 RPC 参数覆盖，前端「严格策略」走的就是这条路。

计划链路另有一组记录用规则名：`plan-sequential`、`plan-pending`、`plan-blocked`、`plan-skipped`、`plan-guard`、`plan-confirmed`、`confirm-required`。它们只出现在审计与回复里，不参与颜色计算。


**注入防御。** 用户输入先归一化再匹配。全角、零宽、同形字都要处理。外部内容（账单备注、短信）只当数据，不当指令。

**审计留痕。** 每条决策一条记录，带前序哈希。评委要求现场改一条记录再校验，你必须能发现。

## 装配层差异

### Cordis

```ts
const ctx = new Context()
ctx.plugin(llmPlugin, { model: "deepseek-chat" })
ctx.plugin(toolsPlugin)
ctx.plugin(policyPlugin)
ctx.plugin(policyPlugin)   // 重复装载自动跳过
```

服务的依赖用 `inject` 声明，缺依赖时插件不启动并给出原因。清理动作用 `ctx.effect()` 注册，进程退出时自动执行。

### pi

```ts
const agent = new Agent({
  state: { messages: [], tools: [] },
  transport,                       // 管模型
  extensions: [toolsExt, policyExt],
  beforeTool: policyGuard,         // 钩子拦截
  afterTool: auditRecorder,        // 钩子记账
})
```

一轮对话由 Agent 驱动，钩子在工具调用前后插入。想加规则就加钩子，不改主循环。

## 扩展点

三条扩展路径，两条路线都支持。

| 要加什么 | 放哪 | 生效方式 |
|---|---|---|
| 新工具 | 运行时注册表 | 重启进程 |
| 新外部服务 | `mcp/servers.json` 加一条 | 重启进程，握手后自动注册 |
| 新技能 | `skills/` 放一个 Markdown | 下次请求自动进目录 |

技能的加载走两段式：系统提示词只放目录摘要，模型需要细节时再调 `skill_load` 取全文。这样新增技能不会撑爆提示词。

## 前端约定

前端只做三件事：发消息、看判定、点确认。

技术栈不限。包里给的是原生 TypeScript 加 Vite，没有框架依赖，改起来快。

页面必须显示三样：判定颜色、命中规则、审计编号。这三样是答辩时的证据。
