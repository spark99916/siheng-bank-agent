# 架构与分层

两条路线共用同一套分层，差异只在第四层怎么装配。

## 五层结构

```
第一层  入口      前端页面 / IM 渠道
第二层  协议      HTTP 或 webhook，统一成内部请求
第三层  编排      意图解析 → 判定 → 确认 → 执行 → 审计
第四层  装配      Cordis 插件 或 pi 三段式
第五层  能力      工具、外部服务、技能、状态
```

分层规矩：只能上层调下层，不许下层反向调上层。第五层不知道有 HTTP，第三层不知道插件怎么写。

## 请求怎么走

一次对话走完六段，每段都可单测。

```
用户说：转给小王 500 元
  ↓ 输入守卫：归一化、注入特征
  ↓ 意图解析：落到 transfer，槽位 payee=小王 amountCents=50000
  ↓ 策略判定：黄，需确认
  ↓ 签发令牌：绑定会话、工具、参数摘要、有效期
  ↓ 执行：确认后扣账，写审计
  ↓ 渲染：数字全部来自工具返回
```

每段都有明确输入输出，接口写在 `docs/03` 的契约表里。

## 接口契约

两条路线的运行时都必须实现这五个接口，名称固定。

| 接口 | 输入 | 输出 |
|---|---|---|
| `chat(sessionId, text)` | 会话标识、用户原话 | 回复、判定、可选确认令牌 |
| `confirm(sessionId, token)` | 会话标识、令牌 | 执行结果或拒绝原因 |
| `cancel(sessionId)` | 会话标识 | 取消结果 |
| `state()` | 无 | 账户、卡片、订阅、持仓快照 |
| `audit(sessionId?, limit?)` | 可选会话、条数 | 审计记录与链校验结果 |

前端只认这五个。换路线不用改前端。

## 数据模型

金额一律整数分，不用浮点。这条不商量，浮点在金额上必然出错。

```ts
interface Account {
  holder: string
  balance: number      // 分
  available: number    // 分，扣掉预锁
}

interface Intent {
  scene: string        // 六个场景之一
  tool: string         // 工具名
  slots: Record<string, unknown>
  missing: string[]    // 缺的槽位，非空就追问
  confidence: number
}

interface Decision {
  level: "green" | "yellow" | "red"
  blocked: boolean
  requiresConfirm: boolean
  hits: Array<{ rule: string; detail: string }>
}
```

## 三条不可让的能力

无论选哪条路线，这三样必须在代码里，不能只在文档里。

**三色判定。** 判定要能解释：为什么黄，命中哪条规则。黑盒判定等于没有判定。

### 判定规则表（与 `shared/rules.ts` 的 `evaluate` 一致）

判定只读 `BankState`，不写任何字段；写状态只发生在工具执行里。

判定的第一维度是**主体**，第二维度才是**操作**：`evaluate(intent, state, { actor, evidence, accountDay, ...阈值覆盖 })`，档位由 `actor.tier` 从 `TIER_POLICY` 取，主体没传就按普通客户。第三个维度是**证据**：外部反欺诈的结论只当证据用，不替代本地判定；第四个是**时间口径**：日累计按账务日算，不按服务器本地自然日。

| `aml-hugging` | 每笔都压在限额的 80%—100% | 参与判黄 / 红 | 区间、限额 |

| `aml-explained` | 证据 ≥ 2 项 | 黄（需确认），**不豁免** | 支持项数、缺项、补凭证口径 |
| `aml-evidence-gap` | 证据 ≤ 1 项 | 红·拦截 | 支持项数、缺口清单 |

AA 收款一律**按总额判限额，不按人均判** —— 按人均判的话拆成 20 个人就能绕过所有限额，而那正是分拆洗钱的形态。

**形状与意图分两条路走。** `shared/aml.ts` 只算读数与证据，模块里没有一行 `level`：`detectSplitPattern` 是纯函数（不读时钟、不读状态），同一批数据问谁算都一样；`collectEvidence` 负责回答「有没有单据、对象、事由」。结论留给 `evaluate`，因此「哪部分是事实、哪部分是判断」在代码结构上就是分开的。由此定死一条：**形状命中永不给绿**，证据 3/3 也只判黄 —— 让 AI 因为「解释得通」就自行放行，是把可解释性换成自我批准。第三项证据带占用校验（一笔消费只能解释一次分摊），否则同一笔消费可以给任意多批转账背书。

阈值分两层：`TIER_POLICY` 是档位矩阵（普通/金卡/私行各一套），`DEFAULT_RISK_POLICY` 等于普通档。`track-pi/src/index.ts` 装配时**只传 `confirmTtlSeconds`，不传阈值** —— 传了就会把档位默认值覆盖掉，这是实测踩过的坑。单次请求可以用第三、四个 RPC 参数覆盖，前端「严格策略」走的就是这条路。

计划链路另有一组记录用规则名：`plan-sequential`、`plan-pending`、`plan-blocked`、`plan-blocked-preview`、`plan-skipped`、`plan-guard`、`plan-confirmed`、`confirm-required`、`plan-compensation`、`plan-rollback`。它们只出现在审计与回复里，不参与颜色计算。

**计划的收尾。** `shared/compensation.ts` 把工具分三类：`compensable`（锁定卡片、预锁资金、生日下单登记、AA 收款单、预约单、申购撤单）、`readonly`、`irreversible`（转账、赎回、取消订阅、挂失、办卡）。执行每一步之前用 `captureUndo` 拍该步会碰到的字段快照；某步判红或执行失败，就按逆序对已执行的步骤调用 undo，`irreversible` 的如实写「撤不掉」并单独留一条审计（`plan_rollback_skipped`）。确认之前会用 `plan-compensation` 把「几步能撤、几步不能」先告诉用户，让承诺与行为是同一套口径。

**依赖前一步的计划步骤。** 生日礼遇是「锁资金 → 生日前下单」两步，第二步的额度来自第一步。`Intent.inPlan` 只有在一个**前置 `birthday_lock` 步骤真实存在**时才会被置上（`parsePlan` 里逐段检查，不按「它在计划里」一刀切放过）。预演阶段它命中 `gift-lock-pending` 而不是 `gift-no-lock`，执行阶段每步实时重算，那时额度已经建好了。

**跨月的定时动作。** 生日下单由 `runDueBirthdayGifts(state, now)` 执行，`track-pi/src/index.ts` 每 60 秒调一次 `agent.tick()`，启动时先补一拍（进程可能几天没开）。`tick` 的 RPC 可显式传时间，验收要确定性地把时钟推到「生日前 2 天」，靠等真实时间过去的测试不叫测试。扣款额必须落在预锁额度内、且预锁未过期，否则如实取消（`gift-cancelled`）而不是硬扣。


**注入防御。** 用户输入先归一化再匹配。全角、零宽、同形字都要处理。外部内容（账单备注、短信）只当数据，不当指令。

**审计留痕。** 每条决策一条记录，带前序哈希。评委要求现场改一条记录再校验，你必须能发现。`shared/persist.ts` 把链追加写到 `data/audit.jsonl`（逐行 fsync），状态与会话用「临时文件 + rename」原子写；启动时装载并校验，`health` 报装载条数、坏行数与链状态。`PERSIST=off` 可退回纯内存。

**外部证据的三种状态。** 没接外部服务（`MCP_RISK_OFF=1`）、接了但调不通（降级）、拿到了结论 —— 这三者在判定里是三种不同结果，不能混成「没查到风险就等于没风险」。

## 装配层差异

### Cordis

```ts
const ctx = new Context()
ctx.plugin(llmPlugin, { model: "deepseek-chat" })
ctx.plugin(toolsPlugin)
ctx.plugin(policyPlugin)
ctx.plugin(policyPlugin)   // 重复装载自动跳过
```

服务的依赖用 `inject` 声明，缺依赖时插件不启动并给出原因。清理动作用 `ctx.effect()` 注册，进程退出时自动执行。

### pi

```ts
const agent = new Agent({
  state: { messages: [], tools: [] },
  transport,                       // 管模型
  extensions: [toolsExt, policyExt],
  beforeTool: policyGuard,         // 钩子拦截
  afterTool: auditRecorder,        // 钩子记账
})
```

一轮对话由 Agent 驱动，钩子在工具调用前后插入。想加规则就加钩子，不改主循环。

## 扩展点

三条扩展路径，两条路线都支持。

| 要加什么 | 放哪 | 生效方式 |
|---|---|---|
| 新工具 | 运行时注册表 | 重启进程 |
| 新外部服务 | `mcp/servers.json` 加一条 | 重启进程，握手后自动注册 |
| 新技能 | `skills/` 放一个 Markdown | 下次请求自动进目录 |

技能的加载走两段式：系统提示词只放目录摘要，模型需要细节时再调 `skill_load` 取全文。这样新增技能不会撑爆提示词。

## 前端约定

前端只做三件事：发消息、看判定、点确认。

技术栈不限。包里给的是原生 TypeScript 加 Vite，没有框架依赖，改起来快。

页面必须显示三样：判定颜色、命中规则、审计编号。这三样是答辩时的证据。
